# opencode — harness anatomy

> opencode is an open-source terminal coding agent written in TypeScript.

## What it is

opencode is built by the SST team (the group behind the SST deployment tool) as a terminal-first coding assistant that lives in the developer's working directory. It can read and edit files, run shell commands, search code, call external tools, and delegate work to sub-agents, all from the command line or an attached web interface.

The single design idea that shapes everything is that the agent is a thin turn-loop over provider runtimes and a durable message store: every turn rebuilds history from a local database, resolves tools and permissions fresh, streams one model turn through an event pipeline, and persists each text, tool-call, and tool-result fragment as parts that later turns can page, prune, summarize, or revert.

## Architecture at a glance

- `packages/opencode/src/session/` — the heart of the harness: the turn loop (`prompt.ts`), the event consumer (`processor.ts`), history access (`message-v2.ts`, `message.ts`, `session.ts`), retries (`retry.ts`), overflow and compaction (`overflow.ts`, `compaction.ts`, `summary.ts`), instructions, todos, and revert logic.
- `packages/opencode/src/session/llm/` — the model-calling layer: `llm.ts` owns the single streaming entry point, `request.ts` prepares requests, `ai-sdk.ts` adapts one provider library, and `native-request.ts` / `native-runtime.ts` provide the alternate native path.
- `packages/opencode/src/provider/` — the model catalog and normalization layer: `provider.ts` builds the provider and model list with capabilities, cost, and limits, `transform.ts` reshapes messages and sampling settings per model, and `error.ts` classifies failures.
- `packages/opencode/src/tool/` — built-in tools with one file per tool (`read.ts`, `write.ts`, `edit.ts`, `glob.ts`, `grep.ts`, `shell.ts`, `task.ts`, `todo.ts`, `skill.ts`), plus shared pieces (`tool.ts`, `registry.ts`, `schema.ts`, `json-schema.ts`, `truncate.ts`, `truncation-dir.ts`).
- `packages/opencode/src/permission/` — the approval gate: `index.ts` stores pending asks and replies, `evaluate.ts` matches ordered allow and deny rules, and `arity.ts` handles shell-command prefix matching.
- `packages/opencode/src/storage/` — durability: `storage.ts` is a generic JSON (JavaScript Object Notation, a text data format) key-value file store and `schema.ts` plus `session/session.ts` define the SQLite (a small local file database) tables for sessions, messages, and parts.
- `packages/opencode/src/snapshot/` and `packages/opencode/src/patch/` — file-state safety: a hidden version-control repository tracks the work folder so a session can be rewound, with `session/revert.ts` tying snapshots to message parts.
- `packages/opencode/src/skill/` and `packages/opencode/src/session/instruction.ts` — knowledge loading: `skill/` discovers and serves on-demand skill files, while `instruction.ts` with `config/markdown.ts` and `project/project.ts` loads memory files such as `AGENTS.md`.
- `packages/opencode/src/mcp/`, `packages/opencode/src/plugin/`, `packages/opencode/src/bus/`, `packages/opencode/src/background/`, `packages/opencode/src/agent/` — extension and concurrency: MCP (Model Context Protocol, a standard for connecting external tool servers) clients, plugin loading and hooks, a global event bus (a shared channel that distributes events), background jobs, and agent definitions with sub-agent permission derivation.

## How each operation works

### 1. Pure LLM call

There is no simple ask-the-model-and-get-text helper in opencode. A LLM (Large Language Model, the AI model that generates text) call always goes through `LLM.Service.stream` in `packages/opencode/src/session/llm.ts`, which resolves the provider client, login credentials, and configuration at the same time. It then calls `LLMRequestPrep.prepare()` from `packages/opencode/src/session/llm/request.ts` to build the system text, message list, tool set, and sampling parameters. By default the request goes to the AI SDK (Artificial Intelligence Software Development Kit, the library used to call models) `streamText()` function with a `wrapLanguageModel` step that rewrites prompts for each provider, passing temperature, token limits, tools, HTTP (Hypertext Transfer Protocol, the web request protocol) headers, and a cancellation signal. The alternate path in `packages/opencode/src/session/llm/native-request.ts` lowers the same intent into a canonical request with system parts and generation settings. In both cases the result is a stream of events, not a single returned string.
**Watch out:** SDK (Software Development Kit)-level retry is forcibly disabled because retry lives higher up in `packages/opencode/src/session/processor.ts`; tools are never sent as an empty list, with a `_noop` fallback tool and per-provider strict-mode fixes in `packages/opencode/src/session/llm/request.ts`.

### 2. Streaming

Each call in `packages/opencode/src/session/llm.ts` creates one cancellation controller per stream and then unifies both runtimes into a single stream of typed LLM (Large Language Model) events such as text pieces and tool calls. The AI SDK (Software Development Kit) path in `packages/opencode/src/session/llm/ai-sdk.ts` converts that library's raw stream into opencode events using adapter state, while the native path in `packages/opencode/src/session/llm/native-runtime.ts` merges model events with tool-dispatch results through a queue. The consumer is `SessionProcessor.process` in `packages/opencode/src/session/processor.ts`, whose event handler switches on text, reasoning, tool-call, tool-result, and step events. As tokens arrive it writes incremental part updates with `updatePart` and `updatePartDelta`, so the user interface and the stored transcript grow piece by piece. The stream ends with a finish event that also carries usage totals.
**Watch out:** the adapter state in `packages/opencode/src/session/llm/ai-sdk.ts` must be reset on the finish event or counters and block identifiers leak into the next stream; orphan text pieces with no preceding start event are silently dropped.

### 3. Conversation state

Conversation history is durable storage, not an in-memory list. Messages and their smaller fragments (called parts) live in a SQLite database accessed with Drizzle (a TypeScript database toolkit), using `MessageTable` and `PartTable` joined by message identifier in `packages/opencode/src/storage/storage.ts` and `packages/opencode/src/session/session.ts`. Reading uses cursor-based pages in `packages/opencode/src/session/message-v2.ts`: newest first, then reversed, with `stream()` looping over pages to rebuild full messages. Before every model turn, `MessageV2.toModelMessagesEffect()` converts stored messages into the model-facing shape, handling images inside tool results and truncation per model, while `filterCompacted()` hides ranges that a summary has replaced. Prompt assembly therefore reloads a fresh projection of history on each turn rather than appending to a cached list.
**Watch out:** some model APIs (Application Programming Interfaces, the interfaces used to call a service) only accept strings in tool results, so `packages/opencode/src/session/message-v2.ts` extracts images and re-injects them as synthetic user messages only when that model supports image input, otherwise surfacing a visible error instead of silently dropping the image.

### 4. System prompt assembly

The system prompt is assembled fresh for every turn in `packages/opencode/src/session/system.ts`. First `SystemPrompt.provider()` picks a static template from `packages/opencode/src/session/prompt/*.txt` by matching the model identifier, falling back to `packages/opencode/src/session/prompt/default.txt` when nothing matches. Each turn then combines the environment block (model and provider identifiers, working directory, whether version control is git, operating system, date, and project references) with loaded instruction files, MCP (Model Context Protocol) additions, and the skill listing, as orchestrated through `packages/opencode/src/session/prompt.ts` and `LLMRequestPrep.prepare`. A final prepare step joins the agent prompt, the template, and any extra system input, and fires plugin hooks that can transform the result. History is appended after this system material, so the model always sees current directory and date context.
**Watch out:** some OAuth (Open Authorization, a login-token standard) and workflow models in `packages/opencode/src/session/system.ts` bypass system-role messages entirely, and plugin-appended system entries beyond the first two are collapsed into one joined block, so their ordering as separate messages is not preserved.

### 5. Provider & model abstraction

The catalog in `packages/opencode/src/provider/provider.ts` is a record (a lookup table) from provider identifier to provider info, each holding its models, built from models.dev data plus environment variables, configuration in `packages/opencode/src/config/config.ts`, and custom sources. Each model entry carries its API (Application Programming Interface) coordinates, capabilities such as temperature support, reasoning, attachments, tool calls, and input and output types, plus context limits, cost, and variants. The `getLanguage()` function resolves a model to a concrete client through per-package loaders, and `packages/opencode/src/provider/transform.ts` normalizes every request per model, including messages, sampling settings, provider options, and the output token cap of 32000. Helpers such as `closest`, `getSmallModel`, and `defaultModel` pick fallback or cheaper models for summaries and constrained tasks. This means adding a new provider mostly means adding catalog data and a loader, not changing the turn loop.
**Watch out:** one gateway integration in `packages/opencode/src/provider/provider.ts` rewrites the client type before variants are computed so reasoning fields use native names, one provider's completion-URL (Uniform Resource Locator, a web address) mode silently strips reasoning options in `packages/opencode/src/provider/transform.ts`, and `getSmallModel()` honors both config and a plugin hook for the cheap-model choice.

### 6. Reliability

Reliability wraps the whole stream, not individual HTTP (Hypertext Transfer Protocol) requests. The `process()` function in `packages/opencode/src/session/processor.ts` runs the stream inside a retry policy from `packages/opencode/src/session/retry.ts`, marking the session status as retrying between attempts. The `retryable()` check excludes context-overflow errors, always retries server (5xx) errors, matches rate-limit, overload, network, and timeout phrases, and maps usage-limit errors to upgrade prompts. Delays prefer the `retry-after` response header when present, otherwise use exponential backoff (waiting longer after each failure: 2 seconds doubling per attempt plus 25 percent random jitter, capped at 30 seconds) with at most 5 attempts. The classifier in `packages/opencode/src/provider/error.ts` separates API (Application Programming Interface) call errors from streamed JSON (JavaScript Object Notation) error payloads and from context overflow detected by message match, status 413, or length-exceeded codes.
**Watch out:** there is no per-request timeout on model calls and no automatic fallback model on error in `packages/opencode/src/session/retry.ts` and `packages/opencode/src/provider/error.ts`; fallback is only the choice of runtime plus routing summaries to the small model, with a `doom_loop` permission question after 3 identical tool calls.

### 7. Tool definitions

Tools are declared with `Tool.define(identifier, Effect)` in `packages/opencode/src/tool/tool.ts`, where the identifier is the short name (for example `read`), the human description comes from a matching `.txt` file, and parameters are an Effect Schema (a TypeScript schema-definition library) structure. A wrapping step adds argument decoding and automatic output truncation. The registry in `packages/opencode/src/tool/registry.ts` builds the built-in tools, adds custom file and plugin tools via `Tool.init`, filters by provider and model, and lets plugins mutate definitions. At call time `SessionTools.resolve` in `packages/opencode/src/session/tools.ts` converts each definition into a model-facing tool object with a JSON (JavaScript Object Notation) schema and an execute closure (a function that remembers its surrounding context) that bridges back into effect execution. Schema normalization in `packages/opencode/src/tool/json-schema.ts` and `packages/opencode/src/tool/schema.ts` with `ProviderTransform.schema` keeps provider-specific shapes consistent.
**Watch out:** the JSON schema is not hand-written but generated from the Effect Schema with local reference inlining and a `WeakMap` (a garbage-collected key-value cache) cache in `packages/opencode/src/tool/json-schema.ts`, with special handling for integer bounds and union types; plugin tools can override the generated schema.

### 8. Agent loop

The outer loop lives in `runLoop()` in `packages/opencode/src/session/prompt.ts`: it creates an assistant message, resolves tools, builds system and model messages, then calls `process()` in `packages/opencode/src/session/processor.ts`. That function calls `LLM.stream` from `packages/opencode/src/session/llm.ts`, adapts the raw stream to events in `packages/opencode/src/session/llm/ai-sdk.ts`, and feeds them to `handleEvent()`, which creates and updates tool, text, reasoning, step, and patch parts. The `process()` result is continue, stop, or compact, and `runLoop` then checks the finish reason, content filters, structured output, compaction and overflow flags, and the agent step limit before either breaking or starting another turn. Each turn is therefore one streaming call plus bookkeeping, and multi-turn behavior emerges from repeating turns. State such as messages, parts, and usage is persisted as the loop goes, so interruption resumes cleanly.
**Watch out:** there is no hand-written loop over tool calls inside a turn: multi-step tool iteration within one turn is owned by the `streamText` call from the AI SDK (Software Development Kit) in `packages/opencode/src/session/llm/ai-sdk.ts`, and opencode only loops at turn level; a doom-loop guard asks a `doom_loop` permission question after 3 identical consecutive tool calls per `packages/opencode/src/session/processor.ts`.

### 9. Parallel tool calls

Parallelism comes from the model runtime dispatching several tool-call events in the same step, not from a single fan-out function. Each call runs its execute closure from `packages/opencode/src/session/tools.ts` concurrently through an effect bridge, as set up by `packages/opencode/src/session/llm.ts`. The processor in `packages/opencode/src/session/processor.ts` tracks each in-flight call by its tool-call identifier with a deferred completion signal, creating `pending` then `running` tool parts via `ensureToolCall` and `readToolCall`. Completion is matched by identifier through tool-result and tool-error events with `settleToolCall`, and cleanup awaits all pending calls concurrently. The registry in `packages/opencode/src/tool/registry.ts` supplies the definitions that make this dispatch possible. Different sessions may also run at once, but within one turn the unit of concurrency is the tool-call identifier.
**Watch out:** there is no single wait-for-all tool executor; unbounded concurrency appears only for definition building, provider setup, and cleanup in `packages/opencode/src/session/processor.ts` and `packages/opencode/src/tool/registry.ts`, so overlapping calls need per-call cancellation signals and identifier-based result matching because assuming serial execution breaks state.

### 10. File tools

Each file tool pairs a parameter schema with an execute function in its own file under `packages/opencode/src/tool/`: `read.ts`, `write.ts`, `edit.ts`, `glob.ts`, and `grep.ts`. Read takes a file path plus offset and limit, edit takes old and new strings plus replace-all behavior, and glob and grep take patterns, paths, and filters, all validated before running. Execution resolves absolute paths, checks external-directory rules, asks the matching permission, then uses filesystem utilities or ripgrep (a fast file-search tool) and returns a title, metadata, and output. Read lists directories with trailing slashes and suggests near-matches on a miss, while write and edit publish filesystem watcher events and attach code-diagnostics output such as language errors. Defaults such as `DEFAULT_READ_LIMIT`, `MAX_LINE_LENGTH`, and `MAX_BYTES` keep outputs bounded.
**Watch out:** limits are easy to get wrong in `packages/opencode/src/tool/read.ts`, `packages/opencode/src/tool/glob.ts`, and `packages/opencode/src/tool/grep.ts`: read truncates any line over 2000 characters and caps output at 50 KB (kilobytes) with offset-continuation hints, glob and grep hard-cap at 100 results with a truncated flag, and edit serializes per file with a one-at-a-time lock, rejects empty old strings, preserves the BOM (Byte Order Mark, invisible file-header bytes), and normalizes line endings.

### 11. Shell execution

Shell commands go through `packages/opencode/src/tool/shell.ts` with prompt help from `packages/opencode/src/tool/shell/prompt.ts`. The command text is parsed with tree-sitter (a syntax-parsing library) grammars for shell languages, a collect step builds a scan of directories, patterns, and always-ask flags, and an ask step requests external-directory plus shell permission before spawning. The `run()` function spawns the child process with the resolved shell, working directory, merged plugin environment, and a timeout defaulting to 2 minutes. Output streams through text decoding, updates live metadata, spills to a truncation-directory file past the byte cap via `packages/opencode/src/tool/truncate.ts` and `packages/opencode/src/tool/truncation-dir.ts`, and the final output keeps the tail plus a truncation notice and timeout or abort notes with the exit code. Live previews let the user watch long commands without waiting for completion.
**Watch out:** unlike generic truncation which keeps the head preview, shell keeps the tail plus a sliding in-memory window of twice the byte cap in `packages/opencode/src/tool/shell.ts`, spilling the full log to disk; process kill uses a 3-second force delay and the live per-chunk preview is separately capped at 30000 characters.

### 12. Permission / approval gate

Every tool calls `ctx.ask()` with its permission kind, patterns, and metadata, which reaches `Permission.ask()` in `packages/opencode/src/permission/index.ts`. Evaluation in `packages/opencode/src/permission/evaluate.ts` checks ordered rulesets with wildcard matching where the last matching rule wins: a deny throws immediately, an allow skips prompting, otherwise it creates a pending entry with a deferred signal, publishes an Asked event, and blocks until a reply of once, always, or reject arrives. An `always` reply appends allow rules and auto-resolves other matching pending asks, while a `reject` fails sibling requests in the same session. Shell prefix logic in `packages/opencode/src/permission/arity.ts` and sub-agent inheritance in `packages/opencode/src/agent/subagent-permissions.ts` refine what each rule covers. Errors surface as typed rejections such as denied, rejected, or corrected permission.
**Watch out:** merging rules is plain array flattening where order decides precedence in `packages/opencode/src/permission/evaluate.ts`; hiding a tool from the list only happens on a full-wildcard deny, shell `always` patterns use token-arity prefixes so flags never count, and sub-agents inherit only parent denies plus external-directory rules with task and todo tools default-denied.

### 13. Session persistence

Live session state lives in the SQLite database through dedicated session tables, not in the generic storage layer. Creation, fetch, and listing in `packages/opencode/src/session/session.ts` insert and select rows defined in `packages/opencode/src/storage/schema.ts` (`SessionTable`, `MessageTable`, `PartTable`) with `fromRow` and `toRow` conversions, slugs, and timestamps. Messages and parts are read and written through the message module plus update helpers such as `updateMessage` and `updatePart`. Resuming a session is just fetching the session row plus its messages and parts, with cost and token totals copied onto the session row. The separate `Storage.Service` in `packages/opencode/src/storage/storage.ts` is a generic JSON (JavaScript Object Notation) key-value file store where key arrays become nested files, used for ancillary data rather than the transcript itself.
**Watch out:** the file store in `packages/opencode/src/storage/storage.ts` uses a per-file transactional re-entrant lock plus a versioned migrations chain, so copying only the session tables loses locking and old-layout migration; session cost and tokens are denormalized (copied) onto the session row rather than computed on read in `packages/opencode/src/session/session.ts`.

### 14. Snapshot & revert

Snapshots use a hidden git repository (Git, a version control system) under the data directory, driven with directory and work-tree flags pointing at the real work folder in `packages/opencode/src/snapshot/index.ts`. The `track()` function stages and commits the work folder and returns a commit hash, and step start and finish message parts store those hashes. Reverting in `packages/opencode/src/session/revert.ts` finds the target message or part, collects later patch parts from `packages/opencode/src/patch/index.ts`, saves the current hash, restores the old state, reverts per file, then writes a session diff and sets a revert marker. Un-revert restores the saved hash and cleanup deletes truncated messages and parts. This gives the agent a file-level undo button tied to conversation position rather than a separate backup tool.
**Watch out:** `packages/opencode/src/snapshot/index.ts` reuses object hashes from the source repository to avoid re-hashing huge checkouts, serializes git access with a per-directory one-at-a-time lock, and passes paths NUL-separated with special quoting rules, so naive path handling breaks on filenames with colons, spaces, or quotes.

### 15. Token accounting & cost

After each model turn, the step-finish handler in `packages/opencode/src/session/processor.ts` calls `Session.getUsage()` in `packages/opencode/src/session/session.ts`. That function normalizes provider-specific cache fields, subtracts cached tokens from input because the underlying library now includes cached tokens in the input count, and splits output versus reasoning tokens, with token shapes defined around `packages/opencode/src/session/message.ts`. Pricing comes from `Provider.Model` cost and tier data in `packages/opencode/src/provider/provider.ts`, picking tiered pricing by context size and computing cost with exact decimal math per million tokens for input, output, cache read, cache write, and reasoning. Totals are added to the assistant message and the step-finish part, and the same token totals feed the overflow check. Users therefore see running cost alongside token counts.
**Watch out:** one provider's usage in `packages/opencode/src/provider/provider.ts` bypasses per-token math via a nano-credit unit, reasoning is charged at the output rate as a workaround, and all inputs pass through safe-number guards because summing raw provider fields would double-count cache and can produce not-a-number or negative costs.

### 16. Context overflow & compaction

The safe input budget comes from `usable()` in `packages/opencode/src/session/overflow.ts`: the model input limit minus a reserve (a config value, or the smaller of 20000 and the maximum output tokens), or the context limit minus maximum output when no input limit exists. The `isOverflow()` check returns true when token totals reach that budget, unless automatic compaction is off or the context size is zero. On overflow the processor flags the need for compaction, and `SessionCompaction` in `packages/opencode/src/session/compaction.ts` keeps only recent turns fitting the preserve budget (default 25 percent of usable budget, clamped between 2000 and 15000 tokens) using estimated token counts with partial-turn splitting. The older head is summarized by a model call built with `buildPrompt` in `packages/opencode/src/session/summary.ts` into a compaction summary pair, while pruning separately blanks old tool outputs by marking their timestamps.
**Watch out:** pruning in `packages/opencode/src/session/compaction.ts` protects the newest 2 turns, 40000 tokens of tool calls, already-summarized messages, and the skill tool, and only writes when pruned estimates exceed 20000, so trimming everything would delete recent evidence and protected tool results (`COMPACTION_BUFFER`, `PRUNE_MINIMUM`, `PRUNE_PROTECT`).

### 17. Tool output offloading

Every tool run is wrapped to pass through truncation in `packages/opencode/src/tool/tool.ts` and `packages/opencode/src/tool/registry.ts`, calling `Truncate.Service` in `packages/opencode/src/tool/truncate.ts`. When line count and byte size fit the limits (config values or the 2000-line and 50 KB defaults), output passes through unchanged. Otherwise the full text is saved to a tool-output file on disk managed by `packages/opencode/src/tool/truncation-dir.ts` under `TRUNCATION_DIR`, and the model only sees a head preview (or tail preview when requested) plus a truncation notice and the saved file path with search and read-with-offset guidance. The result carries content, a truncated flag, and an output path. Files older than 7 days are deleted by an hourly cleanup.
**Watch out:** byte accounting in `packages/opencode/src/tool/truncate.ts` adds newline bytes per line and reports removed units as bytes when the byte cap was hit versus lines otherwise, and the hint text changes when the agent has the task tool, so returning only clipped text with no spill file and no output-path metadata breaks the resume path.

### 18. Memory files

Memory files are project instructions loaded into the prompt without a tool call. The `systemPaths()` function in `packages/opencode/src/session/instruction.ts` collects one global file (the config-directory `AGENTS.md` or home `CLAUDE.md`), then the first project-level match found walking upward so ancestors do not stack, plus extra config globs (filename patterns) and remote URL (Uniform Resource Locator, a web address) entries from `packages/opencode/src/project/project.ts`. The `system()` function reads them in parallel and prefixes each with its source path for the system prompt. The `resolve()` function additionally walks upward from each file read by the read tool and attaches nearby instruction files once per message. The markdown (a plain-text formatting language) loader in `packages/opencode/src/config/markdown.ts` supports `@file` includes and shell-command expansion with strict settings-header parsing plus a permissive fallback.
**Watch out:** nested `AGENTS.md` files do not stack except through on-read resolution in `packages/opencode/src/session/instruction.ts`, `CONTEXT.md` still works but is deprecated, and behavior changes under project-config-disable and prompt-compat flags, so hardcoding a fixed filename list misses these cases.

### 19. Skills / progressive disclosure

Skills are on-demand knowledge packs keyed by name. Discovery in `packages/opencode/src/skill/discovery.ts` scans `SKILL.md` files from global skill directories, upward project directories, config directories, explicit paths, and remote URLs (Uniform Resource Locators) pulled through an index file. Loading in `packages/opencode/src/skill/index.ts` parses each file, requires name and description header data (a settings header at the top of the file), and stores name, description, location, and content in instance state. The system prompt lists only names plus descriptions with `Skill.fmt`, keeping the context small. The full body is injected only when the model calls the `skill` tool in `packages/opencode/src/tool/skill.ts` (described in `packages/opencode/src/tool/skill.txt`), which loads the skill, asks skill permission, lists up to 10 sibling files, and returns the body with base directory and file list.
**Watch out:** a disk skill with the same name overrides the built-in `customize-opencode` skill in `packages/opencode/src/skill/index.ts` because the built-in is registered before disk discovery, and availability is filtered by skill permission, so exposing full bodies up front or skipping permission filtering and override order diverges from the design.

### 20. Sub-agents / delegation

Delegation is a tool call, not a separate API (Application Programming Interface). The `TaskTool.execute()` function in `packages/opencode/src/tool/task.ts` (described in `packages/opencode/src/tool/task.txt`) takes a description, prompt, sub-agent type, optional task identifier, and background flag. It enforces a maximum sub-agent depth (default 1) by walking the parent-session chain, asks task permission, and resolves the agent definition from `packages/opencode/src/agent/agent.ts`. It then creates a child session with the parent identifier (or resumes an existing task identifier) with prompt helpers from `TaskPromptOps`. Child permissions from `packages/opencode/src/agent/subagent-permissions.ts` equal parent denies plus external-directory rules, with task and todo tools default-denied unless the sub-agent explicitly allows them. It runs the prompt in the child session inheriting the parent model unless the agent pins one, and returns the last text part wrapped in a task-state block.
**Watch out:** fresh sub-agents in `packages/opencode/src/tool/task.ts` start with clean context unless a task identifier resumes the same session, and parent agent restrictions do not propagate except denies and external-directory rules, so copying the full parent ruleset over-restricts the child and breaks the design.

### 21. Planning & todo tracking

Todos are per-session rows with content, status, priority, and position managed by `Todo.Service` in `packages/opencode/src/session/todo.ts`. The todo-write tool in `packages/opencode/src/tool/todo.ts` (described in `packages/opencode/src/tool/todowrite.txt`) replaces the whole list transactionally with ordered delete plus insert and publishes an update event. Plan mode is not a flag but two primary agents, `build` versus `plan`, where the plan agent denies edits outside plan files and denies the general task tool while allowing plan exit. Plan exit in `packages/opencode/src/tool/plan.ts` (with `packages/opencode/src/tool/plan-enter.txt` and `packages/opencode/src/tool/plan-exit.txt`) asks a confirmation question then writes a synthetic user message switching the agent back to `build`, with the plan file path coming from `Session.plan()`. In this checkout the plan file only defines the exit tool, with the enter side existing only as prompt text wired through the CLI (Command Line Interface, the terminal commands) and permissions.
**Watch out:** the todo tool in `packages/opencode/src/tool/todo.ts` takes the entire list each call with no per-item patch, requires exactly one in-progress item, and is denied to general sub-agents by default, so making todos global instead of session-scoped or allowing incremental edits diverges from the design.

### 22. MCP / dynamic external tools

External tools arrive over MCP (Model Context Protocol) through `MCP.Service` in `packages/opencode/src/mcp/index.ts`, which holds per-instance state of config, status, clients, definitions, and instructions. Clients are spawned for stdio (standard input and output, a local-process channel), SSE (Server-Sent Events, a streaming HTTP channel), and streaming-HTTP connections through the MCP SDK (Software Development Kit, the client library) rooted at the session directory, with browser helpers in `packages/opencode/src/mcp/browser.ts`. The service paginates the tool list with a tolerant fallback and caches definitions via `McpCatalog` in `packages/opencode/src/mcp/catalog.ts`. At model-call time `packages/opencode/src/session/tools.ts` adapts native definitions into dynamic tools with progress-aware timeout resets, permission-checked per call and plugin triggers around execution, each key namespaced as server plus tool. The tool registry in `packages/opencode/src/tool/registry.ts` itself only uses MCP (Model Context Protocol) tools for a mode description, not for merging them into the built-in list.
**Watch out:** tool names are sanitized in `packages/opencode/src/mcp/catalog.ts` (non-alphanumeric characters become underscores) and namespaced as `server_tool`, while resource keys escape special characters separately, so naively concatenating names or mutating shared definitions breaks keys and cache isolation.

### 23. Hooks, plugins & events

Cross-cutting behavior flows through a global event bus (a shared channel) and plugin hooks. The `GlobalBus` in `packages/opencode/src/bus/global.ts` is a Node event emitter for cross-instance event payloads, auto-assigning each payload an identifier. The `Plugin.Service` in `packages/opencode/src/plugin/index.ts` loads internal authorization plugins plus external plugin origins through `packages/opencode/src/plugin/loader.ts` (resolve target and entry, compatibility check, dynamic import), builds a plugin input of client, project, work folder, and directory, and forwards config and bridge events to each hook's event handler. The key method `trigger(name, input, output)` sequentially awaits each matching hook and returns the mutated output, covering tool definition and before and after-execution hooks. The event manifest in `packages/opencode/src/event-manifest.ts` is a short re-export of event definitions from the shared schema package, with `TriggerName` enumerating hook points.
**Watch out:** only hooks matching an async (asynchronous, running without blocking) input-output shape are triggerable by name in `packages/opencode/src/plugin/index.ts`, and `trigger` mutates and returns the same output object rather than merging return values, so expecting return-value composition misses plugin edits.

### 24. Background & concurrency

Background work is a thin instance-scoped wrapper over a core job registry. The `BackgroundJob.Service` in `packages/opencode/src/background/job.ts` exposes list, get, start, extend, wait, wait-for-promotion, promote, and cancel, and the task tool uses its start, extend, and wait operations with the session identifier as job identifier plus parent and child session metadata to correlate. The `SessionRunState.Service` in `packages/opencode/src/session/run-state.ts` keeps a map of session identifier to runner with idle, busy, and interrupt callbacks, guards concurrent turns through a busy check, and cancel stops both the runner and transitively matching background jobs by identifier and session metadata. Multi-session concurrency is allowed (different sessions run at once) while same-session runs are serialized. The server in `packages/opencode/src/server/server.ts` (HTTP plus interface events) and the control plane in `packages/opencode/src/control-plane/workspace.ts` provide transport and multi-project hosting, not the job queue itself.
**Watch out:** cancellation in `packages/opencode/src/session/run-state.ts` and `packages/opencode/src/background/job.ts` is transitive over the parent and child session graph through metadata matching in a loop, not just exact job identifier, so cancelling only the exact identifier orphans nested sub-agent background jobs.

## Distinctive choices

- Retry lives above the model client, not inside it: `packages/opencode/src/session/llm/request.ts` disables library-level retries while `packages/opencode/src/session/retry.ts` and `packages/opencode/src/session/processor.ts` own backoff, header-aware delays, and error classification.
- Multi-step tool iteration inside one turn belongs to the streaming library call, not to a hand-written loop: `packages/opencode/src/session/llm/ai-sdk.ts` and `packages/opencode/src/session/prompt.ts` show opencode looping only at turn level with one stream per `process()` call.
- Shell output keeps the tail while generic tool output keeps the head: `packages/opencode/src/tool/shell.ts` preserves the end of command logs with a sliding window and disk spill, unlike `packages/opencode/src/tool/truncate.ts` head previews.
- File safety is a hidden version-control repository tied to conversation position: `packages/opencode/src/snapshot/index.ts` and `packages/opencode/src/session/revert.ts` commit the work folder and map hashes onto message parts for revert and un-revert.
- Knowledge is progressively disclosed by default: `packages/opencode/src/skill/index.ts` and `packages/opencode/src/session/instruction.ts` list only skill names and memory-file paths up front and load full bodies on demand or on file read.
- Costs are computed with exact decimal math and provider-specific corrections: `packages/opencode/src/session/session.ts` and `packages/opencode/src/provider/provider.ts` normalize cache counting, split reasoning tokens, and handle tiered pricing and nano-credit units.

## What we take from it

- Copy the single streaming entry point that converges every runtime into one typed event stream (`packages/opencode/src/session/llm.ts`), because it keeps provider quirks in adapters instead of spreading them through the turn loop.
- Copy permission as ordered rules plus an interactive ask with once, always, and reject semantics (`packages/opencode/src/permission/index.ts`), because it makes approvals auditable and sub-agent inheritance a simple deny-propagation rule.
- Copy oversized-output offloading with a disk spill file plus preview and resume hints (`packages/opencode/src/tool/truncate.ts`), because models work better with a pointer to full output than with silent clipping.
- Copy turn-level compaction with a preserve budget, protected recent turns, and a model-written summary (`packages/opencode/src/session/compaction.ts`), because it bounds context without deleting the evidence the next turn needs.
- Do not copy the hidden-repository snapshot machinery or the per-model prompt-template directory (`packages/opencode/src/snapshot/index.ts`, `packages/opencode/src/session/prompt/`) verbatim unless you share opencode's terminal-coding situation: they pay off for local file editing with undo, but add moving parts a hosted or read-only agent does not need.
