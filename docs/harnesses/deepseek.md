# DeepSeek Harness — harness anatomy

> The DeepSeek Harness (`dsh`) is an open-source coding agent written in TypeScript.

## What it is

The DeepSeek Harness is built by DeepSeek AI as a general coding and computer-use agent: it drives a terminal, edits files, remembers project instructions, delegates to child agents, and runs scheduled background work. The inventory records version `0.1.6-alpha.2` at commit `ddefc45`. It is extended mostly by adding small packages rather than by growing a single core, so the repository reads as a large family of focused plugins instead of one program.

The single design idea that shapes everything is that everything is a plugin on the Cordis framework. Cordis is the plugin system underneath: plugins contribute long-lived services, typed events, and reversible registrations to one shared context object. A package therefore never calls another package directly; it publishes a service (for example `ctx.fs` for files, `ctx.shell` for shells, `ctx.tools` for tools) or listens on a shared event (for example `system-prompt/assemble` or `tools/execute`), and the agent behavior emerges from many small packages reacting to the same events.

## Architecture at a glance

- `packages/core/` — the agent core: the agent loop (`packages/core/agent-loop/`), the tool registry (`packages/core/tools/`), the session event log (`packages/core/session/`), the system prompt assembler (`packages/core/system-prompt/`), and the agent identity package (`packages/core/agent/`).
- `packages/llm/` — model access: the provider-neutral runtime and streaming types (`packages/llm/llm/`), the DeepSeek provider adapter (`packages/llm/llm-deepseek/`), retry (`packages/llm/llm-retry/`), token measurement (`packages/llm/token-meter/`), and DeepSeek request-field extensions (`packages/llm/deepseek-llm-api-extensions/`).
- `packages/fs/` and `packages/shell/` — computer work: the filesystem seam plus local backend plus file tools (`packages/fs/fs/`, `packages/fs/fs-local/`, `packages/fs/tool-fs/`, `packages/fs/tool-fs-search/`, `packages/fs/tool-str-replace-editor/`), and the shell seam plus local and sandbox executors plus bash tools (`packages/shell/shell/`, `packages/shell/bash-local/`, `packages/shell/bash-sandbox/`, `packages/shell/tool-bash/`).
- `packages/session/` — conversation durability: the persistence contract and handle (`packages/session/session-persistence/`), the JSONL (JSON Lines, one JSON object per line) storage backend (`packages/session/session-persistence-jsonl/`), checkpoint policy (`packages/session/session-checkpoint-policy/`), and log formatting (`packages/session/session-format/`).
- `packages/context/` and `packages/skill/` — prompt material: system-prompt pieces such as time and file references (`packages/context/time-context/`, `packages/context/file-reference/`, `packages/context/agent-instructions/`), and skill discovery plus the skill-loading tool (`packages/skill/skill/`, `packages/skill/skill-filesystem/`, `packages/skill/tool-skill/`).
- `packages/compaction/`, `packages/spill/`, and `packages/plan/` plus `packages/todo/`, `packages/goal/`, `packages/workflow/` — context and task management: compaction engines and triggers (`packages/compaction/compaction/`, `packages/compaction/compaction-basic/`), output offloading (`packages/spill/spill/`, `packages/spill/spill-policy/`, `packages/spill/spill-local/`), and plan mode, todos, goals, and scripted workflows (`packages/plan/plan-mode/`, `packages/todo/tool-todo/`, `packages/goal/goal/`, `packages/workflow/workflow/`).
- `packages/mcp/`, `packages/hooks/`, `packages/subagent/`, `packages/jobs/`, `packages/schedule/`, `packages/terminal/` — outside connections and background work: the MCP (Model Context Protocol, the standard for external tool servers) client and resources (`packages/mcp/mcp-client/`, `packages/mcp/mcp-resources/`), hook protocol and bridges (`packages/hooks/hook-protocol/`, `packages/hooks/hooks-claude-code/`), child-agent providers (`packages/subagent/subagent/`, `packages/subagent/subagent-spawn-in-process/`), and jobs, reminders, and persistent terminals (`packages/jobs/jobs/`, `packages/schedule/schedule/`, `packages/terminal/terminal/`).
- `packages/interaction/`, `packages/sandbox/`, `packages/subprocess/`, `packages/boot/`, `packages/extensions/`, `packages/client/` — safety and startup: approval gates and permission presets (`packages/interaction/user-approval/`, `packages/interaction/permission-presets/`), sandboxing (`packages/sandbox/sandbox/`, `packages/sandbox/sandbox-policy/`), process spawning (`packages/subprocess/subprocess/`), plugin loading (`packages/boot/plugin-manager/`), dynamic plugin runners (`packages/extensions/cordis-host-runner/`), and user-facing approval UI (user interface) (`packages/client/ui-approval/`).
- A "plugin" is a small package that registers itself on the shared Cordis context when loaded and unregisters when disposed, while a "service" is a long-lived named object on that context (such as `ctx.fs`, `ctx.shell`, `ctx.tools`, `ctx.approval`) that other plugins consume without knowing which package provides it.

## How each operation works

### 1. Pure LLM call

A caller starts with provider-neutral `GenerateOptions` (provider, model, messages, tools, and controls) defined in `packages/llm/llm/src/types.ts`, where LLM means large language model, the AI model that writes the answers. `LlmRuntime.prepareCall` in `packages/llm/llm/src/index.ts` looks up the adapter registration for that provider route and binds exactly one adapter generation to the request. Defaults are resolved with model info in `packages/llm/llm/src/call-config.ts` and the resulting config is deep-frozen so nothing can mutate it mid-flight. The returned `PreparedLlmCall.stream` is one-shot: it rejects reuse or a config mismatch, then dispatches through the captured registration plus the `llm/stream` waterfall event that lets plugins observe or short-circuit. This two-phase shape (prepare, then stream) is what keeps one generation's capabilities from leaking into another endpoint's call.

**Watch out:** prepared dispatch is single-use and bound to one generation, so settings changed between prepare and dispatch cannot mix one generation's capabilities with another endpoint.

### 2. Streaming

Every provider adapter implements `stream`, which returns an async stream of typed `StreamChunk` frames declared in `packages/llm/llm/src/types.ts`: block starts, text deltas, reasoning deltas, tool-call deltas, block ends, usage, and finish. An index on each delta ties interleaved fragments to one content block, and each block end carries the fully assembled block so consumers never reassemble text themselves. `BlockAssembler.push` in `packages/llm/llm/src/assembler.ts` folds chunks in order into partial blocks and records usage and the terminal finish, while `assembleAssistantStream` in `packages/llm/llm/src/assistant-stream.ts` turns the frame stream into assistant content. `LlmRuntime` in `packages/llm/llm/src/index.ts` wraps dispatch in the `llm/stream` waterfall so retry, replay, and routing plugins can observe or short-circuit, then converts adapter throws into terminal error or aborted finishes. The contract is strict about ordering so malformed streams fail visibly instead of corrupting the transcript.

**Watch out:** adapters must send usage before the terminal finish and nothing after it; deltas for an index already closed by a block end are ignored as malformed.

### 3. Conversation state

The conversation is an append-only log of typed session events owned by `Session` in `packages/core/session/src/index.ts`, and that log is the single source of truth. Model history is never stored separately; it is derived by `Session.deriveMessages`, which walks only the events carrying a surface marker defined in `packages/core/session/src/surface.ts` with types in `packages/core/session/src/types.ts`. An append marker adds a node to the tail, while a replace marker shadows an old range with one new node, and the fold result is cached and rebuilt only on replacement. Cross-session views come from `foldSurface` and `deriveEventMessage` in `packages/session/session-projection/src/index.ts`. Because derivation is a pure fold over the log, replay and resume stay consistent by construction.

**Watch out:** `request/header` and `request/context` are log-only events; the latest header rebuilds the next request envelope through `foldRequestHeader`.

### 4. System prompt assembly

Each plugin registers small named pieces — prompt sections, dynamic context snippets, tool-schema providers, and template variables — against the `SystemPrompt` service in `packages/core/system-prompt/src/index.ts` with shapes in `PromptSection`, `PromptContext`, and `PromptAssembly`. Both global and per-agent scoped registrations exist, and a scoped registration hides any global with the same name. Before each model step the agent loop calls `assemble`, which resolves all text providers and sorts sections by a central numeric order and then by name; `packages/context/agent-instructions/src/index.ts`, `packages/context/time-context/src/index.ts`, and `packages/context/file-reference/src/index.ts` are typical contributors. Tool ordering and restrictions are applied, then the `system-prompt/assemble` waterfall event lets further plugins edit the result before the loop renders it with `renderPrompt` and stores it as a system message log node. Scoping plus ordering is what keeps per-agent prompts predictable inside one shared registry.

**Watch out:** a central order table fixes positions from `HARNESS_IDENTITY` at -1000 up to the deployment persona suffix at 10200; a section marked complete forces the whole prompt to that one section after the waterfall still runs.

### 5. Provider & model abstraction

`LlmAdapter` in `packages/llm/llm/src/index.ts` is the abstract provider contract, and only `stream` is required while everything else has defaults. `LlmRuntime` holds adapters in a map keyed by provider-route string, and `registerAdapter` commits routes all-or-nothing, rejects duplicates, and returns a disposer with an atomic replace. The DeepSeek side in `packages/llm/llm-deepseek/src/adapter.ts` and `packages/llm/llm-deepseek/src/index.ts` picks `DeepSeekMessagesAdapter` or `ChatCompletionsAdapter` from the validated connection protocol. Top-level DeepSeek request fields stay separately extensible through `DeepSeekLlmApiExtensionRegistry` in `packages/llm/deepseek-llm-api-extensions/src/index.ts`, whose prepare step merges frozen fields plus a joint accept commit after a successful HTTP (Hypertext Transfer Protocol, the web request protocol) response. Registration-time capture keeps routing decisions explicit instead of depending on ambient global state.

**Watch out:** `listModels` is advisory only so consumers must not reject unlisted model ids and `resolveModel` is the exact-model query; retry policy is captured at registration, so policy changes require a registration replace.

### 6. Reliability

Each provider route owns a retry policy resolved by `resolveRetryPolicy` with shape `RetryPolicyConfig` in `packages/llm/llm/src/retry-policy.ts`, and failures are normalized by `normalizeLlmFailure` into `LlmError` and `LlmFailure` in `packages/llm/llm/src/error.ts`. Normal mode retries only listed retryable codes while always mode retries every failure, and the `dsh-llm-retry` plugin in `packages/llm/llm-retry/src/index.ts` runs that policy on the `agent/request-error` extension point. It logs a durable retry event before a cancellable wait (with history in `packages/llm/llm-retry/src/history.ts`) so retries survive replay, and backoff is exponential with a cap and symmetric jitter. Transport safety comes from timeout helpers — a per-read idle watchdog maps idle streams to a timeout failure and a deadline helper bounds file API (application programming interface, the calls one program makes to another) calls — using `backoff`, `cancellableDelay`, and `idleWatchdog`. Retries therefore stay local to one route and one policy instead of spreading across providers.

**Watch out:** defaults are 5 max retries, 500 ms initial delay, 10 s max delay, 0.1 jitter ratio, retryable empty response, rate limit, server, timeout, and transport errors; no cross-provider fallback was found and retries stay on the same provider route.

### 7. Tool definitions

Authors declare a tool with `defineTool` in `packages/core/tools/src/index.ts`, giving name, description, parameters, output schema, and an execute body, with schema plumbing in `packages/core/tools/src/schema.ts`. One schema language covers both inputs (`ToolDefinition`) and outputs (`ToolOutputDefinition`), and the registry (`ToolRuntime` on `ctx.tools`) shows only name, description, and parameters to the model: timeouts, concurrency flags, and UI functions never go on the wire. One call runs in a fixed order: parse args once, `tools/pre-execute` for allow or deny, guards, `tools/execute` wrappers for timeout and retry, the execute body, `tools/post-execute`, content finalizing, and a `tools/result` notification. Presentation helpers `presentCall` and `presentResult` in `packages/core/agent-tool-presentation/src/index.ts` render calls and results for display, and failures use typed errors for bad args and bad output. The pipeline shape means cross-cutting concerns attach at events instead of inside every tool.

**Watch out:** a provider result carries both schemas and known names so assembly can tell a config typo apart from a deliberately hidden tool; PTC (Program-Tool-Call) mode collapses all direct calls to one reserved `run_code` transport, with sub-calls re-entering the same pipeline.

### 8. Agent loop

A step is one model request plus the tools it calls, and a turn is zero or more steps, driven by `ReactLoopAgent` in `packages/core/agent-loop/src/agent.ts` with per-step state in `packages/core/agent-loop/src/runtime-context.ts` and agent identity in `packages/core/agent/src/index.ts`. Each step assembles the prompt for the owning agent via `assembleContextFor`, prepares the model request from log history, streams the assistant reply, then schedules requested tool calls with `executeToolCalls`. Tool results and extra context commit in model order before the next step, and `InboxTarget` plus `turnBoundary` control injection timing: next-turn versus next-step injection, plus steering, wake, cancel, and maintenance modes. The loop also owns agent creation, scoped registration, and ordered teardown, so child agents and their registrations live and die with the loop that made them. Steps are therefore cheap iterations while turns are the durable unit the session log records.

**Watch out:** the first admitted step reserves the system head before user messages even for an empty prompt, so the prompt travels only as system message history.

### 9. Parallel tool calls

Only an exact true from a tool's `isConcurrencySafe` check makes a call parallel; the scheduler in `packages/core/agent-loop/src/tool-calls.ts` treats missing tools, hidden tools, exceptions, or any other value as exclusive, which is the safe default when unsure. It walks the model's call list in order using `ToolRuntime.executionMode` from `packages/core/tools/src/index.ts`: an exclusive call is a barrier run alone, while parallel calls form a group run in a bounded rolling pool via `runGroup`, capped by `maxParallelToolCalls` with default `DEFAULT_MAX_PARALLEL_TOOL_CALLS` in `packages/core/agent-loop/src/constants.ts`. Later calls are re-classified just before start through `executeToolCalls`, so a call that turns exclusive waits for the pool to drain first. Dispatch may overlap, but results and log events always commit in original model order, keeping concurrent execution deterministic from the model's point of view.

**Watch out:** only `read` and `read_image` declare themselves concurrency-safe while write, edit, bash, glob, and grep stay exclusive by default; the default cap is 10 parallel tool calls.

### 10. File tools

`ctx.fs` in `packages/fs/fs/src/index.ts` is the filesystem seam, an abstract swappable service, and `packages/fs/fs-local/src/index.ts` is the local-disk backend behind it. The `packages/fs/tool-fs/src/index.ts` package owns only schemas, validation, read windows, and log events: reads support line windows plus byte and line-length caps and stream large files instead of loading them whole. Every read logs an observed event recording file presence or absence, and writes and edits pass through single-slot intent guards (`fs/write-intent`, `fs/edit-intent`, `fs/observed`). The optional policy plugin in `packages/fs/fs-observation-policy/src/index.ts` enforces read-before-write using per-session observed state. Search tools in `packages/fs/tool-fs-search/src/index.ts` and the editor in `packages/fs/tool-str-replace-editor/src/index.ts` do not use `ctx.fs` or the shell at all: they spawn the bundled ripgrep binary through `ctx.subprocess` with fixed argument templates (`RipgrepRun`).

**Watch out:** over-cap glob sampling is an explicit deployment choice with a required config and no default; the string replace editor requires an exact unique match of the old text.

### 11. Shell execution

The `bash` tool in `packages/shell/tool-bash/src/index.ts` is a thin consumer of the `ctx.shell` seam defined in `packages/shell/shell/src/index.ts` with `ShellExecutor`, `ShellExecRequest`, `ShellRunResult`, and `ShellProcess`. Each foreground call runs a fresh shell with no state kept between calls, and callers pass a working directory instead of changing directory; resolve fills defaults and caps, run handles foreground execution with timeout kill, and start publishes a background handle registered with the jobs service. The local executor in `packages/shell/bash-local/src/index.ts` spawns through `ctx.subprocess` from `packages/subprocess/subprocess/src/index.ts` with a scrubbed environment (`scrubbedParentEnv`) plus model-friendly overrides. The sandbox executor in `packages/shell/bash-sandbox/src/index.ts` wraps the same argument list through the sandbox service in `packages/sandbox/sandbox/src/index.ts` with policy in `packages/sandbox/sandbox-policy/src/index.ts`, and the persistent variant in `packages/shell/tool-bash-persistent/src/index.ts` serializes per-owner commands. One tool surface therefore rides on two interchangeable executors with identical arguments.

**Watch out:** the child environment strips credential-shaped names and all harness-owned names, then merges back only explicit entries; the persistent bash variant serializes per-owner commands and requires an owning agent.

### 12. Permission / approval gate

The approval service in `packages/interaction/user-approval/src/index.ts` with types `ApprovalService`, `ApprovalPolicy`, and `ApprovalOutcome` in `packages/interaction/user-approval/src/types.ts` is the single gate for whether an action may proceed on `ctx.approval`. A caller requests approval with agent, tool name, call id, and reason; policy never auto-rejects without asking, while policy ask runs a waterfall chain of answerers (including the UI side in `packages/client/ui-approval/src/index.ts`) where the first answer wins and `setApprovalPolicy` swaps the policy. Every ask writes a log-only audit pair of asked plus decided events inside an open turn, and only an allowed-once grant permits that one action, with callers failing closed on rejected, cancelled, or unavailable outcomes. Presets in `packages/interaction/permission-presets/src/index.ts` bundle two independent knobs, sandbox mode and approval policy, into named choices such as workspace-write and full access, while `packages/interaction/tool-ask-user/src/index.ts` (`ask_user_question`) and `packages/guard/timeout-policy/src/index.ts` cover direct user questions and bounded waits. The request deliberately omits tool arguments and links through the call id to avoid drift between what was approved and what runs.

**Watch out:** fail-closed normalization turns a missing, throwing, or off-vocabulary answerer into unavailable; the request omits tool args and links through the call id to avoid drift.

### 13. Session persistence

Storage is reached only through one open handle per session: `SessionHandle` in `packages/session/session-persistence/src/handle.ts` behind the `SessionPersistence` contract in `packages/session/session-persistence/src/storage-contract.ts`. A write handle is the single mutator and a read handle only observes, and live events buffer in a bounded write-behind window (200 ms max delay in the JSONL backend in `packages/session/session-persistence-jsonl/src/storage.ts`) draining as append batches. Only flush promises crash durability, and crash recovery does not truncate: `validateStoredEvents`, `assertContiguous`, and `materializeAppendBatch` return the valid contiguous prefix while the reader appends closers for the interrupted tail (missing tool errors, open step ends, a synthetic interrupted turn end). Semantic checkpoints in `packages/session/session-checkpoint-policy/src/index.ts` decide when to force a flush: the stream event flushes before adapter dispatch, the execute event flushes top-level calls, and the pre-step event flushes the prior step. Failures are fail-closed so an unflushed critical event stops progress rather than risking silent loss.

**Watch out:** semantic checkpoints live in the checkpoint-policy package: the stream event flushes before adapter dispatch, the execute event flushes top-level calls, and the pre-step event flushes the prior step; failures are fail-closed.

### 14. Snapshot & revert

A snapshot is a frozen copy of an event range through `Session.snapshotEvents` and `snapshotSessionEvent` in `packages/core/session/src/index.ts`, with chain helpers in `packages/session/session-format/src/chain.ts`. Resume replays the full stored log as seed, and `Session.fork` (raising `SessionForkError` on misuse) copies a prefix through a boundary into a child seed with an exact inherited event count and a tagged `session/end-seed` marker. Workspace file changes are snapshotted separately from the event log: `workspace/changes` in `packages/deliverables/workspace-changes/src/index.ts` announces working-tree snapshots at turn start and end plus whole-file captures around file-tool edits. Event history and file state are therefore two independent snapshot streams that a reader combines. There is branching and resume but no single undo button.

**Watch out:** no revert verb or symbol was found; the closest durable primitives are fork with a boundary and resume with repair.

### 15. Token accounting & cost

`TokenMeter` in `packages/llm/token-meter/src/index.ts` with types `TokenMeter.measure`, `TokenMeasurement`, `TokenSurfaceNode`, and `TokenUsage` in `packages/llm/token-meter/src/types.ts` replays the durable session tail and returns a detached immutable measurement with log revision, baseline, surface delta, and totals. The effective header's routed provider and model select image pricing through the model service, with heuristics in `packages/llm/token-meter/src/estimate.ts` (`estimateMessage`, `priceSurface`): retained images cost visual tokens plus model-visible text, while other routes keep a fixed heuristic of 4 chars per token with small per-block and per-role overhead. Provider usage counts are disjoint — uncached input plus cache read, cache write, and output — and a provider usage baseline is reused only when the anchor header matches canonically and its total covers the full priced anchor, else an estimated repricing is used. The meter measures pressure on the context window, not money, and cost mentions in source are prose only.

**Watch out:** no monetary cost field exists and accounting is token pressure only; total tokens equal baseline plus surface delta, floored at zero, and cost hits in source are prose only.

### 16. Context overflow & compaction

Automatic work in `packages/compaction/compaction/src/index.ts` (`CompactionEngine`, `CompactionTrigger`, `compactIfNeeded`, `compactNow`) hooks the pre-step event for pressure using the token meter and the request-error event for the canonical context overflow code. Selection in `packages/compaction/compaction-basic/src/region.ts` (`BasicCompactionEngine`, `compactRegion`, `selectCompactableRange`) keeps a priced recent tail, never splits an assistant tool-call and result pair, and skips surface node zero when it is a system prompt. A run appends a compaction start event, summarizes with the model, appends a compaction summary with shadow pricing, then replaces the range with one user message carrying a replace marker; the manual compact command in `packages/compaction/command-compact/src/index.ts` calls `compactNow` while the agent is idle. Optional tool-result pruning in `packages/compaction/compaction-tool-result-pruner/src/index.ts` (`ToolResultPruner.pruneSession`) runs before summary selection to shrink the range cheaply. Recovery runs inside the open step and retries only when pruning or summarization advances the replacement generation.

**Watch out:** shadow-price protocol means a replace must sit directly after its metering event so plain consumers can subtract cost without per-node state; recovery runs inside the open step and retries only when pruning or summarization advances the replacement generation.

### 17. Tool output offloading

Two separate paths in `packages/spill/spill/src/index.ts` (`SpillStore.saveText`, `SpillRef`, `SpillLocator`) bound oversized outputs, driven by policy in `packages/spill/spill-policy/src/index.ts` with local files in `packages/spill/spill-local/src/store.ts`. Spill policy listens on the post-execute event: plain-text results over the inline byte cap are saved verbatim to a session-scoped private file, then replaced in-model with a bounded head and tail preview plus a retrieval notice that still fits the cap. Image offload appends a durable offload decision (`offloadOldestImages`) naming the oldest retained image occurrences, and later requests send placeholder text instead of the pixels. The retainer library in `packages/util/output-retention/src/index.ts` (`TextRetainer`, `ItemRetainer`, `PRUNE_MARKER`) is only the mechanical bounding helper with exact omission counts. Spilling keeps the model input bounded while the full bytes stay retrievable on disk.

**Watch out:** best effort means with no session owner, no spill backend, or a save failure, the inline result is kept and success never turns into an error; the read tool is skipped by the model-facing arm to avoid a spill loop.

### 18. Memory files

This is the AGENTS.md style memory loader in `packages/context/agent-instructions/src/index.ts` with config in `packages/context/agent-instructions/src/config.ts` (`loadBaselineInstructionSet`, `discoverBaselineInstructionFiles`, `findProjectRoot`, `renderAgentInstructions`, `reconcileInstructionContext`). Before the first request it walks up from the session folder using version-control markers to find the project root, then loads ordered candidates plus local overlays plus the user-global file. Files are read through the filesystem service with per-file byte caps and a total budget, duplicates are collapsed, then the set is rendered once into durable conversation context. After that, successful read, write, and edit tool uses touch nested or changed instruction files into the inbox for reconciliation, and an identity string covering root, markers, budgets, and candidate lists lets resume detect a changed baseline. Memory is therefore files on disk with a load-once plus reconcile-later rhythm.

**Watch out:** default candidates are `AGENTS.md` and `CLAUDE.md` with local overlays `AGENTS.local.md` and `CLAUDE.local.md` and `.git` as the project root marker; no separate vector or long-term memory store was found in these paths.

### 19. Skills / progressive disclosure

Skills are local instruction packs that stay unloaded until needed, with the merging registry (`SkillProvider`, `SkillCandidate`, `SkillSummary`, `SkillDefinition`, `renderSkillContent`) in `packages/skill/skill/src/index.ts`. Providers such as `FileSystemSkillProvider` in `packages/skill/skill-filesystem/src/index.ts` discover directory-bundle or flat Markdown (a lightweight text format) skills with YAML (YAML Ain't Markup Language, a config text format) frontmatter from project, custom, user, and bundled roots. The tool package in `packages/skill/tool-skill/src/index.ts` publishes a durable session catalog of names plus descriptions and one model tool to load a single full body on demand. That is progressive disclosure: a short list first, full text only when needed, and a user typing a slash name for a user-invocable skill injects the same canonical skill content block as instructions context. Rank decides duplicates across roots so project skills beat bundled ones.

**Watch out:** lower rank wins duplicate names across roots, from project files at 100 up to bundled skills at 600; names must match lowercase alphanumeric words joined by single dashes.

### 20. Sub-agents / delegation

`ctx.subagents` in `packages/subagent/subagent/src/index.ts` (`SubagentRuntime`, `SubagentProvider`) is a named-provider registry behind one interface, surfaced to the model by the tool in `packages/subagent/tool-subagent/src/index.ts`. Same-process providers such as `SpawnInProcessProvider` in `packages/subagent/subagent-spawn-in-process/src/index.ts` run each child as a fresh child agent on the same Cordis context with its own session and system prompt and zero parent conversation. Out-of-process providers such as `ClaudeCodeProvider` in `packages/subagent/subagent-claude-code/src/index.ts` invoke the official agent SDK (software development kit) CLI (command-line tool) in the parent workspace through the subprocess service. Foreground calls dispose after collection while background calls own a job or a continuable child id (`startContinuable`), and Agent Teams in `packages/experimental/agent-team/src/index.ts` (`TeamService`) is a separate lead-plus-teammates layer with roster, mailbox, task board, and journal over the lead session log. Children therefore start blank by design and only the collected result returns to the parent.

**Watch out:** spawn and Claude Code providers do not inherit parent context; default delegation depth is 1, and the subagent tool preflights the child model route and model selection.

### 21. Planning & todo tracking

Plan mode in `packages/plan/plan-mode/src/index.ts` (`PlanModeController`, `EXIT_PLAN_MODE`) is logged per-agent collaboration state: while active a deployment-owned guidance section is added and the exit tool presents the full plan for user approve or keep-planning review. Todos in `packages/todo/tool-todo/src/index.ts` (`todo_write`) are whole-list replacement — each write call appends a snapshot, replay is last-write-wins, and the list clears on the next turn start. Goals in `packages/goal/goal/src/index.ts` (`GoalService`) are same-session event-sourced objectives with compare-and-set mutations and phases for active, paused, blocked, and complete, where the round driver in `packages/goal/goal-round-driver/src/index.ts` (`renderGoalRoundPrompt`) auto-queues one followup prompt per round at quiescence. Workflows in `packages/workflow/workflow/src/index.ts` (`WorkflowEngine`) run orchestration scripts that fan out to subagent children, and Ralph in `packages/workflow/tool-ralph/src/index.ts` (`RALPH_SCRIPT`) is a fixed foreground loop starting one fresh structured-output child per round with only the immutable objective plus a bounded prior handoff. Planning, lists, goals, and scripted loops are four separate small systems, not one task engine.

**Watch out:** the exit tool stays registered while inactive so the tool catalog is stable; todo config switches single versus multi in-progress discipline, and Ralph defaults to 256 max rounds with 16384 chars each for handoff and result.

### 22. MCP / dynamic external tools

Each client plugin instance in `packages/mcp/mcp-client/src/index.ts` (`StdioConfig`, `StreamableHttpConfig`, `startConnection`, `registerServerContext`) connects to one external MCP server over a spawned stdio (standard input/output, the child-process pipes) child process or streamable HTTP, with connection mechanics in `packages/mcp/mcp-client/src/connection.ts`. It then registers that server's tools on the tool registry under server-qualified names of the form server plus raw name (`publicToolName`). Lifecycle is effect-scoped: disposal disconnects, unregisters tools, and releases the server name reservation, and live code swap disposes and recreates the connection. Resources are separate in `packages/mcp/mcp-resources/src/index.ts` (`McpResourceRuntime`): the resource runtime keeps scoped per-server providers and exposes three shared model tools for listing and reading plus a system-prompt section listing live server names. One plugin instance therefore equals one server connection with clean teardown.

**Watch out:** server names allow up to 32 letters, digits, dashes, and underscores, and a duplicate name in the same scope throws; tool call timeout defaults to 60 s and startup errors do not fail by default, with a backoff reconnect policy.

### 23. Hooks, plugins & events

The hook protocol in `packages/hooks/hook-protocol/src/index.ts` with the runner in `packages/hooks/hook-protocol/src/runner.ts` (`runHook`, `parseHookOutput`, `matchesMatcher`, `mergeHookOutputs`) is a shared non-plugin library for matching, shell execution, output decoding, restrictive merging, and detached quiescence. The bridge in `packages/hooks/hooks-claude-code/src/index.ts` mounts unmodified Claude Code command hooks onto harness points such as session start, pre and post tool use, stop, and subagent start and stop: it reads the hooks config once, runs each matched command with a JSON (JavaScript Object Notation, the text format tool schemas use) payload on standard input, logs invoked and result events, and folds decisions. The plugin manager in `packages/boot/plugin-manager/src/index.ts` (`PluginManager`) handles current-profile composition and bundles through the package manager with file locks and protected modules. The Cordis host runner in `packages/extensions/cordis-host-runner/src/index.ts` (`DynamicCordisRunnerService`) defines dynamic Cordis plugins from host or client source strings and sandboxes host code in a VM (virtual machine, an isolated code-execution box) with precheck plus human-approved client activation, exposed to the model through `packages/extensions/tool-cordis/src/index.ts`. Hooks, bundles, and dynamic plugins are three distinct extension paths with different trust levels.

**Watch out:** updated input and system messages returned from Claude hooks are logged or warned but not honored; the dynamic runner VM timeout defaults to 5 s.

### 24. Background & concurrency

Jobs separate contract from storage: `packages/jobs/jobs/src/index.ts` (`JobRegistry`, `JobId`, `JobStatus`) owns the abstract seam with session-id fenced access and first-wins settlement, while `packages/jobs/jobs-local/src/index.ts` (`LocalJobRegistry`) is the in-memory process-local registry with per-owner concurrency caps and owner cleanup. The tool package in `packages/jobs/tool-jobs/src/index.ts` attaches the controller letting producers start work plus three model tools (`job_output`, `job_list`, `job_kill`) to list, read with bounded waits, and kill. Unreported completions are injected into a busy owner's next step or wake an idle owner, so results never get lost when nobody is listening. Schedule in `packages/schedule/schedule/src/index.ts` (`ScheduleRuntime`) is agent-scoped durable one-shot and fixed-rate reminders over the session log, driven only for root agents. Terminal in `packages/terminal/terminal/src/index.ts` (`TerminalSessionService`) is an owner-scoped persistent PTY (pseudo-terminal, an interactive shell session) registry where backends own mechanics and the service owns ids, publication, authorization, and awaited cleanup.

**Watch out:** max 10 concurrent jobs per owner by default; tool waits default to 30 s with a 600 s cap and at most 3 consecutive wakes, and a background subagent one-shot settles through jobs.

## Distinctive choices

- Single-use prepared model calls (`packages/llm/llm/src/index.ts`): prepare binds one generation to one route and rejects reuse, so capability settings cannot drift between prepare and dispatch.
- The conversation log is the only state and history is a fold (`packages/core/session/src/index.ts`): nothing stores model messages separately, and replace markers shadow ranges instead of editing them.
- A central numeric order table rules the whole system prompt (`packages/core/system-prompt/src/index.ts`): positions run from `HARNESS_IDENTITY` at -1000 to the deployment persona suffix at 10200, and scoped registrations hide globals with the same name.
- Parallelism is opt-in per tool with exclusive barriers as the safe default (`packages/core/agent-loop/src/tool-calls.ts`): only `read` and `read_image` run concurrently while everything else serializes.
- Crash recovery repairs instead of truncating (`packages/session/session-persistence-jsonl/src/storage.ts`): the reader keeps the valid contiguous prefix and appends closers for the interrupted tail.
- Shadow pricing keeps compaction honest (`packages/compaction/compaction-basic/src/region.ts` with `packages/compaction/compaction/src/index.ts`): a replace marker must sit directly after its metering event so plain consumers subtract cost without per-node state.

## What we take from it

- Copy the seam-plus-backend split (`packages/fs/fs/src/index.ts` with `packages/fs/fs-local/src/index.ts`, `packages/shell/shell/src/index.ts` with `packages/shell/bash-local/src/index.ts`): the model-facing tool depends on an abstract service while the backend is swappable, which makes sandboxing a one-line executor swap.
- Copy the event-waterfall extension points (`packages/core/system-prompt/src/index.ts`, `packages/llm/llm/src/index.ts`, `packages/core/tools/src/index.ts`): retry, routing, prompt edits, and tool wrappers attach as observers instead of edits inside every tool and every call.
- Copy the opt-in concurrency plus in-order commit rule (`packages/core/agent-loop/src/tool-calls.ts`): default-exclusive tools with ordered result commit keep parallel execution deterministic from the model's point of view.
- Do not copy the monorepo scale itself (dozens of packages under `packages/` with per-package registries, presets, and bridges): that structure serves a team shipping many surfaces, and a small harness should start with one tool registry, one session log, and one executor.
- Do not copy the DeepSeek-specific adapter and field-extension machinery (`packages/llm/llm-deepseek/src/adapter.ts`, `packages/llm/deepseek-llm-api-extensions/src/index.ts`) verbatim: the protocol picks and per-field registries encode this project's provider, and a new harness needs only the adapter interface plus one implementation.
